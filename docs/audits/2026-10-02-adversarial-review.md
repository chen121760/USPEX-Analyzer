# 功能修复后的对抗性审查

日期：2026-10-02。审查基线：`b4fcbb6`。开始审查时工作区干净，上一轮业务修改已经提交。

发现 **7 项可复现缺陷：4 项 P1、3 项 P2**。主要风险是项目切换丢修改、新项目混入旧结构，以及不完整输入产生错误的形成能和凸包距离。本次提交增加复现工具与审查记录，没有修改业务代码。

## 复现方式

在仓库根目录运行：

```powershell
node scripts/runAdversarialReview.mjs
```

脚本调用正式的解析器、领域函数、Zustand store，并通过 TypeScript AST 提取正式的自动保存 hook、数据表列定义与单元格回调。替换的边界是 React hook 容器、时钟和数据库写入；能量与凸包算法没有另写一份。每个场景断言正确行为，当前基线输出 `7 defect(s) reproduced; 3 invariant(s) passed`，退出码为 **1**。修复后应逐项变为 PASS。

自动保存的时序检查使用可控时钟。A2 特别模拟防抖计时到期时导入仍在等待绘制，不代表每次无效导入都会丢修改。本轮没有用浏览器逐项重演以下场景。

三个通过的对照场景：普通备注修改能在防抖后保存；同一组边界结构按二元系统计算得到正确凸包距离；真实解析的固定组分 TiH 能导入同压力的元素二元工作台。因此没有把“固定组分 numSpecies 必然不兼容”记为缺陷。

## P1：优先处理

### A1. 切换项目会丢失前一项目尚未保存的修改

位置：[usePersistence.ts](../../src/hooks/usePersistence.ts#L60)。本轮保存重构引入了命名项目也受此影响的回归。

复现：先保存命名项目 A；修改 EA1 的备注；在 2 秒防抖结束前载入 B；再执行剩余保存计时器。

实际写入快照是 `[["A",""],["B",""]]`，A 的新备注从未进入保存队列。切换后内存中的 A 也被替换，重新打开 A 只能拿到旧备注。标签修改等通过同一路径保存的数据同样受影响。

原因：`schedule()` 取消旧计时器，计时器到期时再读取当前 store。旧项目快照没有在修改时捕获，项目切换也没有提交其待保存修改。串行队列只能保证已入队快照的顺序，无法保护尚未入队的数据。此前备注和结构标签的 action 会立即调用命名项目保存，上一轮删除了这些调用。

修复要求：按项目保留待保存快照；切换前把旧项目待保存数据入队，再处理新项目。验证最终命名项目记录和当前会话记录，不能只测试队列顺序。

### A3. 新解析的项目混入旧项目的手动结构和自定义标签

位置：[useProjectStore.ts](../../src/store/useProjectStore.ts#L224)。遗留缺陷。

复现：载入 Ti-H 项目，添加 `[1,1]` 手动结构和 `A-only` 标签；调用正式 `processFiles()`，成功解析一个只有 Si 元素的新项目。

实际：新项目普通结构为一个 Si 结构，但 `userStructures` 仍含 `[1,1]`，标签仍含 `A-only`。导出这个新项目后，`validateProject()` 报 `Invalid structure identity or composition`，无法重新导入。

原因：解析成功时替换了系统信息、普通结构和项目 ID，但没有重置手动结构、标签及筛选预设。JSON 加载与原始文件解析采用两套项目替换逻辑，后者缺少完整的数据隔离。

修复要求：统一新项目快照的初始化与替换；保留旧项目前先完成 A1 的保存，随后清理旧项目附属数据。覆盖跨元素数量的新建、导出、重新载入全过程。

### A4. 三元工作台退化到一条边时把稳定端元判成不稳定

位置：[workshopHull.ts](../../src/lib/workshopHull.ts#L291)。遗留算法缺陷。

复现：系统声明 `[Ti,H,Li]`，当前可见组只含 Ti-H 边上的四个结构：Ti 的焓 −2、H 的焓 −1、两个 TiH 的焓分别 −2.5、−2 eV/atom。Li 参考缺失，但这些结构都不含 Li，它们的形成能仍有定义。

正确凸包距离为 `[0,0,0,0.5]`。实际结果为 `[1,1,0,0.5]`，单位 eV/atom：Ti、H 两个端元被错误排除出稳定相。相同输入按二元系统计算得到正确结果。

原因：共线的组分点没有三维下凸包面，备用分支直接用所有形成能的全局最小值作为每个组分的凸包能量。不同组分之间不能这样直接做能量排名。工作台隐藏一个含 Li 的组或导入部分数据即可出现这种退化。

修复要求：按数据的有效维数构建低维凸包；共线数据按组分坐标插值，而非减全局最低形成能。覆盖边界子系统、少量点和共面数据。

### A5. 缺少总能量的 JSON 被接受，但每原子焓被当成晶胞能量

位置：[normalizeStructure.ts](../../src/domain/structure/normalizeStructure.ts#L80)、[validateProject.ts](../../src/domain/project/validateProject.ts#L41)。遗留单位转换缺陷仍可通过新校验进入。

复现：Ti/H 参考焓为 −2/−1 eV/atom；导入 TiH₃，字段为 `composition:[1,3], enthalpy:-3, fitness:0`，省略 `enthalpyTotal`。校验和项目载入均成功，再导入工作台计算。

正确晶胞总能量为 −12 eV，形成能为 −1.75 eV/atom。实际规范化写入总能量 −3 eV，形成能为 **+0.5 eV/atom**，使稳定性结论反转。上一轮修复了手动输入模态框的这项转换，但 JSON 规范化入口仍有同类问题。

修复要求：明确缺失字段的迁移规则；已知每原子焓时根据原子总数补全晶胞能量，或者拒绝不能确定单位的输入。不能把同一数值同时默认给两种单位。

## P2：数据完整性与恢复

### A2. 保存计时器在加载期间到期后不再重试

位置：[usePersistence.ts](../../src/hooks/usePersistence.ts#L65)、[持久化字段比较](../../src/domain/project/persistence.ts)。本轮新增时序缺口。

复现：A 有尚未保存的备注；开始一次最终被拒绝的项目导入；保存计时器在 `isLoading=true` 时到期；导入失败，A 的内存数据被保留，加载状态恢复。

实际：该计时器跳过写入，加载结束也没有新计时器；备注一直未保存，直到再次发生持久化数据变更。脚本实际调用了无效 `loadProjectFile()`，没有用另一份加载实现代替它。

原因：`isLoading` 不属于 `projectDataChanged` 比较的字段，加载结束不会重新调度被跳过的保存。

修复要求：保留 dirty 状态；加载结束或失败时重新安排待保存快照。既排除进度更新，也不能丢掉加载生命周期的保存恢复动作。

### A6. 筛选导出的项目仍携带被删除结构的未收敛统计

位置：[filteredProject.ts](../../src/domain/project/filteredProject.ts#L10)、[DashboardPage.tsx](../../src/modules/Dashboard/DashboardPage.tsx#L266)。本轮新增导出入口的统计遗漏。

复现：原项目 3 个结构，其中 1 个未收敛；筛选后只导出 1 个收敛结构。

实际：导出结构数为 1，`unconvergedCount` 仍为 1。重新载入后仪表盘直接显示该旧计数，与导出数据矛盾。`minEnthalpy`、`maxFitness` 也沿用原系统信息，没有按选择重建。

修复要求：统一从导出结构重建所有数据统计，来源说明明确为筛选数据。检查的不应只有 `totalStructures/stableCount/totalGenerations` 三项。

### A7. JSON 的非能量数值字段未校验，导入成功后表格渲染抛异常

位置：[validateProject.ts](../../src/domain/project/validateProject.ts#L41)、[DataTablePage.tsx](../../src/modules/DataTable/DataTablePage.tsx#L350)。遗留输入问题未被本轮校验覆盖。

复现：合法结构的 `volume` 改为字符串 `"30"`，载入项目。

实际：没有拒绝输入，旧项目被替换。正式 `hasVolume` 判断返回 true，正式体积单元格执行 `.toFixed(3)`，抛出 `getValue(...).toFixed is not a function`。现有“导入失败保留旧数据”的保护没有触发，因为 schema 认为这是有效项目。

修复要求：校验全部渲染、计算所需的已知字段类型，以及嵌套数组内容；允许的缺失值通过明确迁移处理，不能把字符串原样交给数值访问器。
